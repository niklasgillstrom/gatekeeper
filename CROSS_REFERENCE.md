# Cross-reference — Article claims ↔ reference-implementation code

**Purpose.** This table maps every testable technical claim made in Article 1 (Gillström, in preparation; target venue: *Capital Markets Law Journal*), Article 2 (Gillström, in preparation; target venue: *Computer Law & Security Review*), and the `HARDWARE_BASELINE.md` document to a concrete code path, test, documentary artefact, or an honest "gap" flag. It is intended to let a peer reviewer confirm, claim-by-claim, whether an assertion is backed by executable code, by documentary evidence, by the article's own argument, or by nothing yet. Section numbers refer to the manuscripts as revised on 2026-10-30; the code is release 1.7.0 of the three repositories.

**Status codes.**

- **CODE** — the claim is backed by executable code in one of the three repos under this tree. Reviewer can exercise the path with `mvn -B test` or by running the application. CODE does not mean that the path has been run against real hardware or a real external service: where a path is tested only against test doubles (a test JCA provider instead of an HSM, a local RFC 3161 service instead of a qualified one, a reference HTTP server instead of a payment-network operator), the row says so.
- **DOC** — the claim is backed by `HARDWARE_BASELINE.md`, by an external vendor document, or by a published certification/standard whose URL is cited.
- **TEXT-ONLY** — the claim is theoretical, normative, or citation-based. It does not require code backing (e.g. a reference to Julia Black 2008, a DSR methodology citation, a reading of DORA recitals). Listed here so reviewers can see that the claim has been considered and classified.
- **GAP** — the claim plausibly *should* have executable or documentary backing in these repos and does not yet. Flagged so that a reviewer can see honest limitations up front.

**Repository references.** Paths are rooted at `hsm/` (shorthand: `[HSM]`), `gatekeeper/` (shorthand: `[GK]`), or `railgate/` (shorthand: `[RG]`). File paths are given relative to these roots. Each of the three repositories (hsm + gatekeeper + railgate) carries its own copy of this `CROSS_REFERENCE.md`; the three copies are identical.

**Triadic system overview (since v1.2.0).** The reference implementations form a three-component system:

- **`[HSM]`** — financial-entity-side HSM attestation verification core ([10.5281/zenodo.19930310](https://doi.org/10.5281/zenodo.19930310), concept DOI)
- **`[GK]`** — NCA-operated supervisory gatekeeper API; from v1.1.0 also exposes `POST /api/v1/verify` for settlement-time signature verification; from v1.7.0 also runs as an organisation-internal gatekeeper (profile `org`) ([10.5281/zenodo.19930395](https://doi.org/10.5281/zenodo.19930395), concept DOI)
- **`[RG]`** — central-bank settlement-rail enforcement layer; calls `[GK]/api/v1/verify` at settlement time ([10.5281/zenodo.19952991](https://doi.org/10.5281/zenodo.19952991), concept DOI)

**The quadruple triangulation.** Article 1 §6.2 and Article 2 §9.3 describe the triadic architecture as a triangulation model over four independent data sources ("quadruple triangulation" in the artefact documentation): (1) Getswish AB's allocation register (*tilldelningsregister*), (2) the gatekeeper audit log, (3) the RIX-INST settlement log, and (4) the recipient-side transaction registration. Of the four, the code produces one: the gatekeeper audit log (`[GK]/src/main/java/eu/gillstrom/gatekeeper/audit/AppendOnlyFileAuditLog.java`). The other three are external to these repositories: the allocation register is kept by Getswish AB, the settlement log by the Riksbank as operator of RIX-INST, and the transaction registration by the recipient's bank. railgate's own decision log (`RailgateAuditLog`, in memory) and its replay journal record railgate's decisions; they are not the RIX-INST settlement log. The four-source model operates at settlement; it complements the three-source triangulation at certificate issuance (Article 1 §4.2: the banks, Getswish AB and the HSM manufacturers' root certificates), which `[GK]` implements as an inquiry procedure (rows Art 1 §4.2 and §5.2 below). Across the supervisor boundary at settlement time only digest, signature and certificate identifiers travel.

**External-document references.** Citations to `HARDWARE_BASELINE.md §X.Y` resolve to a separate document — *Gillström, HARDWARE_BASELINE.md (in academic submission package)* — that is **not** part of any of the code repositories. It is a sibling artefact to Article 1 (CMLJ) and Article 2 (CLSR) in the academic submission folder, documenting the operational case-study deployment (Securosys Primus, YubiHSM, FIPS-mode configuration, audit-log pipeline, time-sync infrastructure, attack-vector review). Peer reviewers receive HARDWARE_BASELINE.md as part of the submission bundle alongside the two articles and these three repositories; it is intentionally excluded from the public MIT-licensed repos because it carries device serial numbers, invoice references, and operational configuration that belong in a controlled submission folder, not in a public Zenodo deposit. Anonymous Zenodo readers will see the citations but cannot resolve them; that is the intended scope.

## GAP summary

The following items remain open in release 1.8.0. A peer reviewer should interpret these as honest limitations of the reference implementation at submission time — items that the articles describe, or that a production deployment needs, but that the code does not yet demonstrate. Items that earlier drafts of this document listed and that have since been closed are no longer listed here; the rows above carry their CODE status directly: persistent registry storage, the hash-chained per-entry-signed audit log, rate limiting, NCA-role authorisation, the production receipt-signing key, the signed batch export, and, in 1.7.0, the organisational deployment variant (profile `org`), the COSE export, RFC 3161 timestamping (implemented; only a local TSA tested), the lifecycle events Rotated, Revoked and Decommissioned, the triangulation procedure as a single in-code check, and registry tamper evidence through the inventory fields in the chained audit log. The former item "forward-secure key rotation per Ma–Tsudik (2008)" is withdrawn rather than closed: the design is now an HSM-bound, non-exportable log key, attested at start-up, plus external RFC 3161 timestamps of entries or of the chain head (Article 2 §6.3).

1. **Marvell attestation format for Azure / Google / Marvell** — `MarvellAttestation.java` in both repos follows Marvell's published attestation page and `verify_pubkey.py`, Microsoft's parser and Google's chain check; whether the vendors' blobs use that layout awaits a real attestation (`MARVELL_FORMAT_UNCONFIRMED`). No FIPS information is read from these blobs.
2. **Owner chains for cloud HSMs** — Both repos check Google's owner chain under Hawksbill Root v1 prod. Microsoft's validator anchors its partition chain at a self-signed certificate from the submitted bundle, so no pinned Microsoft owner root exists to check.
3. **Real signatory-rights registry adapter** (Swish agreement registry / Bolagsverket) — `[HSM]` ships only `FailClosedSignatoryRightsVerifier` (production-safe default; rejects every query) and `MockAgreementRegistrySignatoryRightsVerifier` (JSON file). The FE must implement a custom adapter against its authoritative registry.
4. **No real HSM and no real TSA tested** (Art 2 §5.1 FR5, §5.3 STR5, §6.3, §8.5) — the HSM-held log key is tested with a test-only JCA provider (the SunPKCS11 path is implemented but not exercised), the log-key attestation with vendor-shaped evidence on a test PKI (a test shows the production verifier refuses it), and RFC 3161 with a BouncyCastle TSA in process and over loopback HTTP. No qualified TSA has been used; TSA certificate revocation is not checked; only YUBICO and SECUROSYS attestations of the log key are supported, checked once at start-up and for the active key only. Removal of an entry token or an anchor record is not detected by the chain check (both are outside the entry hash); anchors protect against the key holder only once a third party has retrieved them.
5. **Payment-network operator interface not offered** — railgate's client and the specification `[RG]/api/payment-network-operator.openapi.yaml` exist, but no operator provides the endpoint, nothing has been tested against Getswish AB or another operator, and which field of Swish's payout API corresponds to `payoutInstructionId` is not established.
6. **Triangulation state** — inquiries are held in memory only (a restart discards them; audit entries of reports already generated remain); bank-reported certificate fields are not compared; the registry is not frozen per inquiry; report submissions are not audited individually; certificates are not matched across jurisdictions.
7. **Mutation testing of the 1.7.0 code — closed 2026-10-31** — PIT 1.30.1 (`-Ppit`, 100 % threshold in each `pom.xml`) detects every mutant in all three repositories: hsm 2 274 of 2 274 (6 by timeout), gatekeeper 3 208 of 3 208 (16 by timeout), railgate 497 of 497. Rebuilt with the tests added for it (`mvn -B clean verify`, then `e2e/run.sh`): hsm 494, gatekeeper 772, railgate 206 tests, 0 failures; e2e 17 tests, 0 failures, the same 7 skipped; the tests and the package-private seams added are listed in each repository's `CHANGELOG.md` (1.7.0, Tests).
8. **Build with the 1.7.0 dependency versions — closed 2026-10-31** — built and tested with the 1.7.0 versions (Spring Boot 4.1.2, Jackson 3.2.4 / 2.22.4, springdoc-openapi 3.2.0, swagger-ui 5.34.1, Tomcat 11.0.27): hsm 485, gatekeeper 723, railgate 185 tests, 0 failures; e2e 17 tests, 0 failures, 7 skipped. OWASP Dependency-Check 13.0.0 with NVD and Sonatype OSS Index: no finding at CVSS 7 or higher after the two Spring Security suppressions in gatekeeper's and railgate's `.owasp-suppressions.xml`; logback-classic 1.5.38 reports CVE-2026-19880 and CVE-2026-104721 (CVSS 6.3; an MDC-based discriminator flowing into a nested FileAppender path, which none of the three repositories configures). Remaining caveat: the two Spring Security suppressions rest on Spring's advisories against Sonatype's data and are pinned to 7.1.2.
9. **FIPS reporting is Yubico-only and does not establish certification** — the code does not map firmware to a FIPS 140 or Common Criteria certificate; the FIPS indicator (`41482.4.10`) is reported, not interpreted; no real attestation carrying the FIPS-approved flag (`41482.4.12`) is in the repositories, so the requirement's success path is tested only with synthesized certificates and mocked verifier results; Entrust nShield's FIPS 140 Level 3 world binding is verified but not reported, and the relation of Crypto4A's `qasm-certified-production` claim to FIPS-approved mode is not established, so with the requirement on every non-Yubico attestation is refused.
10. **Registry journal not hash-chained** — the journal itself carries no hash chain or signature; tamper evidence for the settlement-relevant fields comes from the audit log's inventory fields, and no code compares the two.
11. **Lifecycle responses and `SIGNED` events** — status-change responses (`ROTATED`, `REVOKED`, `DECOMMISSIONED`) are not signed, only their audit entries; a `SIGNED` event accepts only `SHA512withRSA` and no certificate PEM.
12. **COSE export envelope** — the COSE form has no inspection id, chain head, generation time or completeness proof; omitted entries are detectable only through the hash links between consecutive exported entries, and the seal is by the active key, not by the key that signed each entry.
13. **railgate replay record and verdict binding** — the replay record is local to one instance, never pruned, not tamper-evident, and has no release for a settlement that fails downstream after `ALLOWED`; `sv1` carries no per-call nonce, so a genuine verdict for an identical `(certSerial, issuerDn, digestHex)` can be presented again within the skew window; the validity and revocation of pinned operator and gatekeeper certificates are not checked.
14. **Binding at settlement** — the digest is supplied by the payment-network operator and railgate cannot bind it to the settled pacs.008; refunds of Swish Handel payments are denied (`DORA_32_AUDIT_MISSING`). Both need participation conditions for the rail (`[RG]/README.md`).
15. **Local end-to-end coverage** — of the 17 e2e tests, 7 are skipped without material that cannot be produced locally: the hsm issuance path needs a real BankID signature (4), and an allowed settlement and `CERT_REVOKED` need a signature made with the attested fixture key (3).
16. **Trust anchors: confirmed against the manufacturers on 2026-10-31; overrides checked for form only** (Art 1 §4.3; `[GK]/README.md` §3.6) — every pinned anchor is confirmed against the manufacturer's own material (the real Yubico and Securosys attestations, Google's and Fortanix's published samples, Entrust's example warrants, Thales's, Marvell's and Crypto4A's published roots). An override (`gatekeeper.trust-anchors.*`, `swish.trust-anchors.*`) is checked for form, not for validity, BasicConstraints, key usage or key size; the Thales, Crypto4A and Fortanix key-hash checks apply to the pinned constants only; the Marvell roots cannot be replaced per vendor; in `[GK]` the `yubico` and `securosys` overrides also govern the log key's attestation; `[HSM]` reports overrides only in its start-up log.

18. **BankID signing act: not confirmed against a production signature** (`[HSM]` `BankIdConsentPolicy`, `swish.bankid.require-signing-act`, on by default since 1.8.0) — the mandate must be the signature of a signing order: `clientInfo/funcId` in the signed data is `Signing`, and the signatory's certificate asserts the nonRepudiation key usage. Both are those of the signature format as FriBID documents it (https://fribid.se/dev-docs/signature-format.html); BankID's own documentation says that `/auth` takes `userVisibleData` as `/sign` does and that the specification of the signature is delivered on request. No production signature was available here: the fixture is synthetic, and the four e2e tests that need a real signature are skipped (item 15). A deployment confirms the two values on a signature of its own before relying on the default; `false` restores the behaviour of 1.7.0, in which the signature of an identification was accepted as a mandate.

These GAPs do not invalidate the articles' central claims, which are *demonstrated* by the CODE rows above. They do delimit the scope of the reference implementation versus the scope of the argument: the articles argue what the mechanism does in principle and what the case-study hardware instantiates in practice, while the reference implementation demonstrates the verifier core, the supervisory and organisational gatekeeper, the settlement-rail enforcement layer, and the FE-side integration pattern. Closing the GAPs is a production-deployment concern, not a scientific-claim concern, and each is documented either inline in this table or in `HARDWARE_BASELINE.md`.
